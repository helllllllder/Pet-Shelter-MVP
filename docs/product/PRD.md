## Project Overview

Luna's Pet Central is an offline-first, single-user, multi-shelter operations management tool for animal shelters to enable fast hypothesis validation. It replaces fragmented, paper-based processes with a unified digital solution covering the full operational lifecycle: pet registration and health tracking, pet lifecycle management, veterinary appointment management with a reusable directory of clinics and professionals, pet care scheduling with proactive reminders, categorized inventory control, and maintenance scheduling.

**Primary Goals**:

1. Provide a single authoritative source of truth for all pet and shelter data.
2. Eliminate the risks associated with paper-based record management.
3. Maintain shelter-scoped data separation on a single device.
4. Support multi-shelter operations on a single device in Phase 1.
5. Enable transparent data sharing with veterinary partners and adoption candidates via configurable, revocable shareable links (Phase 3+).
6. Track the complete lifecycle of each pet from intake through adoption, transfer, foster, or death (Phase 3+ for shareable links).

**Business Reasoning**: The organization currently operates without any digital management system. The inability to efficiently track and retrieve pet medical histories, manage supplies, and coordinate maintenance represents a significant operational risk and limits the shelter capacity to scale. Phase 1 validates the core workflows offline before investing in cloud infrastructure.

### Shelter Context

In Phase 1, a single operator manages one or more shelters on a local device. The operator selects the active shelter context; all CRUD operations, searches, and views are scoped to that shelter. From Phase 3 onward, multiple authenticated users can share shelter access with role-based permissions.

> **Terminology Note**: Throughout this document, "Staff" is used as the generic actor in functional requirements. In Phase 1 (offline MVP), "Staff" refers to the single **Operator** managing shelters locally. Multi-user staff operations with role-based access are introduced from Phase 3 onward.

## Technical Process Flow

The following describes the logical workflow of the primary operational processes within Luna's Pet Central.

### 1. Operator Registration and Local Shelter Setup Flow

1. A new operator launches the application for the first time.
2. The system presents a local profile registration form (name, contact/email).
3. The operator completes the form; the system stores the profile locally.
4. The operator creates a new shelter by providing a shelter name and optional details.
5. The system creates the shelter and sets it as the active context.
6. The operator can create additional shelters at any time and switch between them via the shelter selector.
7. All subsequent operations are scoped to the active shelter.

### 2. Pet Registration Flow

1. Authenticated Staff or Admin member initiates a new pet registration.
2. Staff completes the registration form including intake origin selection (if 'Other' is selected, a secondary free-text field appears), health details, and optionally checks the 'DOB Estimated' flag.
3. Staff optionally toggles the 'Available for Adoption' flag.
4. System validates required fields and creates the pet profile record.
5. The pet profile is immediately available to all authorized staff at the shelter.

### 3. Veterinary Appointment Flow

1. Staff creates a new appointment record linked to a specific pet.
2. Staff selects the clinic and veterinarian from the directory (or adds a new entry).
3. Staff enters appointment date and notes.
4. Staff optionally creates care events directly within the appointment, which are auto-linked.
5. Staff uploads any received documents (PDFs or images) as attachments.
6. Appointment record, care events, and attachments are stored on the pet's profile.

### 4. Pet Care Event Flow

1. Staff creates a care event record for a pet, selecting the modality.
2. If applicable, staff enters the substance/product name (optional).
3. Staff configures the recurrence interval and end date (if temporary).
4. Staff optionally links the event to an existing vet appointment.
5. Staff optionally selects an inventory item and decrement quantity (inventory usage template, FR21). If stock is insufficient, the system warns and saves the care event without the inventory decrement.
6. System schedules future occurrences and triggers proactive reminders at 7 days, 3 days, and 1 day before each occurrence is due (FR18), plus an on-due-date notification (FR17).
7. Staff log completion of each event instance as it occurs.

### 5. Inventory Management and Alert Flow

1. Staff logs a new inventory item, selecting a category and entering all required fields.
2. Staff configures alert rules for the item (quantity threshold or expiry window).
3. Staff configures notification mode: Standard (in-app) or Custom (+ email and/or push).
4. System evaluates inventory levels against configured rules continuously.
5. When a rule triggers, the system delivers notifications in the configured mode.
6. If email/push delivery fails after 3 retries, the system flags the notification as 'FAILED' and displays a non-dismissible in-app banner to the intended recipient until acknowledged (FR25).
7. Staff manually update quantity when items are consumed or restocked (or use inventory usage templates from care events, FR21).

### 6. Maintenance Task Flow

1. An authorized Staff or Admin member creates a maintenance task with type, description, and scheduled date.
2. Staff optionally assigns the task to a specific staff member.
3. All shelter staff receive a notification (Standard or Custom). If assigned, the assignee receives an additional individual notification.
4. Staff mark the task as completed when finished; the system logs the completion event.
5. Overdue tasks remain visible and trigger reminders.

### 7. Profile Sharing Flow

1. Staff navigates to a pet's profile.
2. For Adoption Profile links: the pet must have the 'Available for Adoption' flag active.
3. Staff selects link type (Adoption or Veterinary) and configures TTL (maximum 90 days).
4. System generates an anonymous URL with the appropriate visibility scope.
5. Staff shares the URL with the intended recipient.
6. Recipient accesses the link without a system account.
7. Before a link expires, Staff can renew it to reset the TTL (maximum 90 days from renewal).
8. Staff can navigate to the link management view and manually revoke any active link at any time.

### 8. Pet Archiving and Transfer Flow

1. Staff navigates to a pet's profile and sets the outcome status (Adopted, Deceased, Transferred Internal, Transferred External, or In Foster).
2. **If 'Adopted'**: System presents the Adopter Details form (Name, Phone, Address). Staff must complete all fields before the adoption is finalized. On confirmation, the pet is archived with adopter details stored.
3. **If 'Deceased'**: System archives the pet immediately. Full history is preserved.
4. **If 'Transferred (Internal)' *(Future — v2.0+)***: Staff selects the destination shelter (must be another Luna's Pet Central shelter). System creates a shadow record — original shelter keeps a read-only copy of the full history, destination shelter receives a new active profile referencing the original.
5. **If 'Transferred (External)'**: System archives the pet at the originating shelter with no shadow record.
6. **If 'In Foster'**: Pet status is updated to 'In Foster' without archiving. Pet remains in active views. When the pet returns, staff clear the 'In Foster' status.
7. For all archiving outcomes: the 'Available for Adoption' flag is automatically cleared, pending care events are cancelled (see Edge Cases), and the pet is removed from active operational views and dashboard counts.
8. All active shareable links are automatically revoked. The system strictly forbids creating new shareable links for the archived pet.

### 9. Notification Failure Escalation Flow

1. A notifiable event triggers (care event reminder, inventory alert, maintenance task).
2. System delivers the in-app notification immediately (always delivered).
3. If the user has configured Custom mode, the system attempts email and/or push delivery.
4. On delivery failure, the system retries up to 3 times with backoff.
5. If all retries fail, the notification is flagged as 'FAILED'.
6. System displays a non-dismissible in-app banner to the intended recipient containing the failure details and the original notification content summary.
7. The banner persists until the recipient clicks 'Acknowledge'.
8. Acknowledgment is logged in the audit trail.

---

### 10. Report Generation and Consumption

*Note: Report Generation (FR32–FR36) is introduced in Phase 4 (Reporting & Discovery). Per-shelter Dashboard Overview (FR31) is available in Phase 1 (MVP).*

1. **Initiate**: Admin or Staff selects a report type (e.g., Pet Census, Inventory Status) and configures filters.
2. **Query**: The system queries the database, strictly scoped to the active shelter context.
3. **Render**: The system renders the results on-screen with pagination for large datasets.
4. **Export**: The user optionally exports the full dataset (e.g., CSV/PDF format).

### 11. Dashboard and Search Usage

*Note: Per-shelter Dashboard Overview (FR31) and Pet Search & Filtering (FR30-A) are active in Phase 1 (MVP). Inventory Search (FR30-B) and Maintenance Task Search (FR30-C) are introduced in Phase 4.*

1. **Dashboard Load**: User navigates to the Dashboard view.
2. **Aggregation**: The system calculates and displays key KPIs (active pets, pets in treatment, foster pets, care events) for the active shelter.
3. **Search Initiation**: User inputs a query into the Search bar.
4. **Result Rendering**: The system returns matched results across pets (Phase 1) and inventory/maintenance tasks (Phase 4) within the shelter context.
5. **Navigation**: User selects a result to navigate directly to its detail view.

### 12. Data Export Flow

*Note: Data Export (FR03-A, FR03-B) is scheduled for Phase 2 (Operational Enrichment).*

1. The operator navigates to the data export view.
2. The operator selects the export scope: a specific shelter or all shelters.
3. The system compiles all records (pets, care events, appointments, vet directory, media references) for the selected scope.
4. The system generates a portable export file.
5. The operator selects a local destination and the export is saved.
6. The system confirms successful export completion.

- `In Foster → Active`: Staff clears 'In Foster' status (pet returned).
- `Active → Adopted → Archived`: Staff sets outcome to 'Adopted', completes Adopter Details form. Pet is archived.
- `Active → Deceased → Archived`: Staff sets outcome to 'Deceased'. Pet is archived.
- `Active → Transferred (Internal) → Archived`: Staff selects destination shelter. Shadow record created at original shelter. New active profile created at destination.
- `Active → Transferred (External) → Archived`: Pet is archived at originating shelter. No shadow record.

### 2. Maintenance Task Lifecycle

```
┌─────────┐    ┌──────────┐    ┌─────────────┐    ┌───────────┐    ┌──────────┐
│ Created │───▶│ Assigned │───▶│ In Progress │───▶│ Completed │───▶│ Archived │
└─────────┘    └──────────┘    └─────────────┘    └───────────┘    └──────────┘
     │
     ▼
┌─────────┐
│ Overdue │  (scheduled date passes without completion)
└─────────┘
```

**Transitions:**

- `Created → Assigned`: Staff assigns a task to a specific staff member. (Optional — tasks can remain unassigned.)
- `Created/Assigned → In Progress`: Staff begins working on the task.
- `In Progress → Completed`: Staff marks the task as completed. Timestamp and staff attribution logged.
- `Completed → Archived`: System archives completed tasks after a retention period.
- `Created/Assigned → Overdue`: Scheduled date passes without task being marked in progress or completed.

### 3. Shareable Link Lifecycle

```
┌────────┐    ┌─────────┐
│ Active │───▶│ Expired │  (TTL elapses)
└────────┘    └─────────┘
     │
     ├───────▶┌─────────┐
     │        │ Revoked │  (manual revocation)
     │        └─────────┘
     │
     └───────▶┌─────────┐
              │ Renewed │──▶ Active  (TTL reset, returns to Active)
              └─────────┘
```

**Transitions:**

- `Active → Expired`: TTL elapses without renewal. Link becomes permanently invalid.
- `Active → Revoked`: Staff manually revokes the link. Immediate, permanent invalidation.
- `Active → Renewed → Active`: Staff renews the link. TTL is reset from renewal timestamp (max 90 days). Link returns to Active state.

### 4. Notification Lifecycle

*Note: The full Notification Lifecycle (including email/push retry and failure escalation) applies from Phase 2 onward. Phase 1 uses local in-app alerts only (Pending → Delivered).*

```
┌─────────┐    ┌───────────┐
│ Pending │───▶│ Delivered │  (successful delivery)
└─────────┘    └───────────┘
     │
     ▼
┌────────────┐    ┌────────────┐    ┌────────────┐    ┌────────┐    ┌──────────────┐
│ Retrying   │───▶│ Retrying   │───▶│ Retrying   │───▶│ Failed │───▶│ Acknowledged │
│ (attempt 1)│    │ (attempt 2)│    │ (attempt 3)│    │        │    │              │
└────────────┘    └────────────┘    └────────────┘    └────────┘    └──────────────┘
```

**Transitions:**

- `Pending → Delivered`: Email/push delivery succeeds on first attempt.
- `Pending → Retrying (1)`: First delivery attempt fails.
- `Retrying (1) → Retrying (2)`: Second attempt fails.
- `Retrying (2) → Retrying (3)`: Third attempt fails.
- `Retrying (N) → Delivered`: Any retry attempt succeeds.
- `Retrying (3) → Failed`: All 3 retry attempts exhausted. In-app banner displayed.
- `Failed → Acknowledged`: User acknowledges the failure banner. Acknowledgment logged.

### 5. Care Event Lifecycle

```
┌───────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────┐    ┌───────────┐
│ Scheduled │───▶│ Reminder Sent│───▶│ Reminder Sent│───▶│ Reminder Sent│───▶│ Due  │───▶│ Completed │
│           │    │   (7 days)   │    │   (3 days)   │    │   (1 day)    │    │      │    │           │
└───────────┘    └──────────────┘    └──────────────┘    └──────────────┘    └──────┘    └───────────┘
     │
     ▼
┌───────────┐
│ Cancelled │  (pet archived — all pending events cancelled)
└───────────┘
```

**Transitions:**

- `Scheduled → Reminder Sent (7d)`: 7 days before due date, system sends reminder.
- `Reminder Sent (7d) → Reminder Sent (3d)`: 3 days before due date.
- `Reminder Sent (3d) → Reminder Sent (1d)`: 1 day before due date.
- `Reminder Sent (1d) → Due`: Due date reached. On-due-date notification sent.
- `Due → Completed`: Staff logs completion of the care event occurrence.
- `Scheduled → Cancelled`: Pet is archived. All pending/future occurrences are cancelled.

> **Phase Note**: The Reminder Sent states (7d, 3d, 1d) apply from Phase 4 onward when FR18 (Proactive care event reminders) is implemented. In Phases 1–3, the Care Event lifecycle is: `Scheduled → Due → Completed` (or `Scheduled → Cancelled`).

### 6. Invite Link Lifecycle

*Note: The Invite Link Lifecycle applies from Phase 3 (Online Foundation) onward. It is not applicable in Phase 1 (offline MVP).*

```
┌─────────┐    ┌──────────┐
│ Pending │───▶│ Redeemed │ (user authenticates with matching email)
└─────────┘    └──────────┘
     │
     ├───────▶┌──────────┐
     │        │ Expired  │ (TTL elapses)
     │        └──────────┘
     │
     └───────▶┌──────────────┐
              │ Invalidated  │ (admin resends invite or revokes)
              └──────────────┘
```

**Transitions:**

- `Pending → Redeemed`: User successfully authenticates via Google SSO using the Identity-Bound email.
- `Pending → Expired`: 30-day TTL elapses.
- `Pending → Invalidated`: Admin manually revokes the invite or resends it (invalidating the old link).

### 7. Appointment Lifecycle

```
┌────────┐    ┌──────────────┐
│ Active │───▶│ Soft-Deleted │ (staff deletes appointment)
└────────┘    └──────────────┘
```

**Transitions:**

- `Active → Soft-Deleted`: Staff deletes the appointment. It is hidden from active views but retained for referential integrity.

## Domain Model

Conceptual model of the core domain entities and their relationships:

```
Shelter
 ├── Operator (single local user — Phase 1)
 │     └── [Multi-user roles: Admin, Staff, Read-only — Phase 3+]
 ├── [Invite Links — Phase 3+]
 ├── Pets
 │     ├── Care Events
 │     │     └── Inventory Usage (optional link)
 │     ├── Vet Appointments
 │     │     └── Documents (PDF, Images)
 │     ├── Photos / Videos
 │     ├── [Shareable Links — Phase 3+]
 │     └── Adopter Details (on adoption)
 │
 ├── Inventory Items
 │     └── Alert Rules
 │
 ├── Maintenance Tasks
 │
 ├── Local Alerts (in-app due-date notifications)
 │
 └── Data Exports
```

**Key Relationships:**

- A **Shelter** contains all other entities. Data isolation is enforced at this boundary.
- In Phase 1, a single **Operator** manages all shelters locally. From Phase 3 onward, multiple **Users** can belong to shelters with different roles.
- A **Pet** belongs to exactly one Shelter (active profile). A shadow record may exist at a previous shelter for internally transferred pets.
- A **Care Event** belongs to a Pet and may optionally link to one Vet Appointment and one Inventory Item (usage template).
- A **Vet Appointment** belongs to a Pet and references entries in the Veterinary Directory. It may have multiple Documents attached.
- A **Shareable Link** belongs to a Pet and has a type (Adoption/Veterinary), TTL, and lifecycle status.
- An **Inventory Item** belongs to a Shelter and may have multiple Alert Rules.
- A **Maintenance Task** belongs to a Shelter and may be assigned to a User.
- A **Notification** is generated by the system for a triggering event and targets one or more Users. It tracks Delivery Status per channel (in-app, email, push).
- **Adopter Details** are a one-to-one association with a Pet, populated only when the pet's outcome is set to 'Adopted'.
- **Invite Links** are generated by Admins, scoped to a Shelter, single-use, Identity-Bound to a specific email, and expire after 30 days. Resending an invite invalidates the previous pending link.
- A **Data Export** captures a snapshot of one or more shelters' complete data for portability.

## Considerations

### Risks


| Risk                              | Description                                                                                                                    | Mitigation                                                                                                                                             |
| :--------------------------------- | :------------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Data Migration                    | No existing digital records to migrate, but paper records may need manual entry at go-live.                                    | Plan for a structured data entry period at launch with clear staff guidelines.                                                                         |
| User Adoption                     | Staff with limited technology experience may resist the new system.                                                            | Prioritize simple, intuitive interface design (NFR01) and provide staff orientation.                                                                   |
| Media and Document Storage Volume | Pet photos, videos, and veterinary documents may grow to significant storage volumes over time.                                | Design storage capacity with scalability and file size limits from the outset.                                                                         |
| Notification Reliability          | Staff must trust that in-app, email, and push alerts will arrive consistently and correctly.                                   | Implement reliable notification delivery with a 3-retry policy and failure escalation (FR25).                                                          |
| Shareable Link Misuse             | Veterinary Profile links contain sensitive medical data; if shared with the wrong recipient, this is a data exposure risk.     | Require explicit confirmation step when generating a Veterinary link; support instant revocation (NFR12); enforce maximum 90-day TTL (FR27).           |
| Concurrent Access Conflicts       | Multiple staff editing the same inventory item or pet record simultaneously could cause data loss.                             | Concurrent Access Conflicts — Applicable from Phase 3 onward when multi-user access is introduced. Phase 1 single-user operation eliminates this risk. |
| Local Data Loss                   | In Phase 1, all data is stored locally on a single device. Loss, damage, or reset of the device results in complete data loss. | Encourage regular data exports (FR03). Display periodic in-app reminders to export data.                                                               |


### Assumptions

- Phase 1 targets a single operator on a single device managing one or more shelters locally, validating core workflows offline.
- The operator has access to a single device capable of running the application. No internet connectivity or external account is required for Phase 1.
- In Phase 1, the operator is the sole user. Staff management via invite links is introduced in Phase 3.
- Veterinary documents are assumed to be received digitally (scanned or photographed) before upload.
- Records are kept indefinitely; hard-delete is supported only for verified GDPR compliance requests (NFR16).
- Phase 1 shelters are fully independent local data containers. Cross-shelter features (internal transfers, shadow records) are deferred to Future (v2.0+).

### Dependencies

- Local device storage is required for all data persistence in Phase 1.
- The operator must be able to digitize (scan/photograph) paper veterinary documents before upload.
- Google SSO, internet connectivity, and email/push delivery become dependencies from Phase 3 onward.

### Constraints

- MVP scope excludes: adoption payment processing, public donation management, volunteer shift scheduling, and automated duplicate pet detection.
- Inventory stock levels are adjusted manually by staff — except when using the optional 1-click inventory usage template during care event recording (FR21), which decrements the specified quantity.
- In Phase 1, all access is scoped to the active shelter context on the operator's device. There is no multi-user access control. From Phase 3 onward, access is role-gated per shelter with no global platform administrator role (NFR08).
- Shareable links have a maximum TTL of 90 days and cannot be made permanent (FR27).

## Glossary


| Term                         | Definition                                                                                                                                                                                                                                             |
| :---------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **BRD**                      | Business Requirement Document — a formal document describing the business goals, current process, scope, and requirements of a project.                                                                                                                |
| **PRD**                      | Project Requirement Document — a technical companion to the BRD detailing specific functional and non-functional requirements.                                                                                                                         |
| **MVP**                      | Minimum Viable Product — the minimum set of features required to launch a functional version of the platform.                                                                                                                                          |

| **FeLV**                     | Feline Leukemia Virus — a viral disease specific to cats tracked as part of the pet health profile.                                                                                                                                                    |
| **Vermifuge**                | A medication used to eliminate internal parasites (worms) from an animal.                                                                                                                                                                              |
| **RBAC**                     | Role-Based Access Control — an access management model where permissions are assigned to roles rather than individual users.                                                                                                                           |
| **Google SSO**               | Google Single Sign-On — an authentication mechanism allowing users to sign in using their existing Google account credentials.                                                                                                                         |
| **Shadow Record**            | A read-only copy of a pet's record created in a receiving shelter during an internal transfer, linking back to the original record in the originating shelter.                                                                                         |
| **Identity-Bound**           | An invitation or access mechanism that is strictly tied to a specific user's identity (e.g., their authenticated Google email address). The link cannot be forwarded to or redeemed by a different email address.                                      |
| **Invite Link**              | A URL generated by a shelter administrator that allows an unregistered user to join the shelter with a pre-assigned role upon authentication via Google SSO. Identity-Bound to a specific email address.                                               |
| **Inventory Usage Template** | A pre-configured template that defines specific inventory items and quantities to be decremented in a single action during care event recording.                                                                                                       |
| **Soft Delete**              | A deletion method where the record is marked as inactive rather than permanently removed, preserving referential integrity with linked records.                                                                                                        |
| **In Foster**                | A pet lifecycle outcome status indicating the animal has been placed in a temporary foster home but remains under the shelter's responsibility.                                                                                                        |
| **Adopter Details**          | Contact information (Name, Phone, Address) captured for the person adopting a pet, stored securely and accessible only to authorized shelter personnel.                                                                                                |
| **DOB Estimated Flag**       | A boolean flag on a pet profile indicating that the recorded date of birth is an estimate rather than a known date.                                                                                                                                    |
| **Shareable Profile Link**   | A URL generated by the system granting anonymous, read-only access to a defined subset of a pet's profile data.                                                                                                                                        |
| **TTL**                      | Time-to-Live — a configurable duration (maximum 90 days, renewable) after which a shareable link automatically expires.                                                                                                                                |
| **Intake Origin**            | The source from which a pet arrived at the shelter (e.g., street rescue, owner surrender).                                                                                                                                                             |
| **Archived Pet**             | A pet whose outcome status has been set to a terminal outcome (Adopted, Deceased, or Transferred). Its full history is preserved but it no longer appears in active operational views. Note: 'In Foster' is a reversible, non-archival status — fostered pets remain in active views. |
| **Inventory Alert**          | A system notification triggered when an inventory item reaches a configured quantity threshold or approaches its expiration date.                                                                                                                      |
| **Care Event**               | A recorded instance of a treatment, vaccine, vermifuge, or other care activity administered to a pet.                                                                                                                                                  |
| **Vet Directory**            | A shared, searchable registry of veterinary clinics and professionals maintained within the platform.                                                                                                                                                  |
| **Tombstoning**              | A data deletion technique where the record is not physically removed from the database, but its sensitive PII fields are replaced with a predefined placeholder (e.g., `[GDPR ERASURE VERIFIED]`) to maintain referential integrity in immutable logs. |
| **Shelter Context**          | The active shelter a user is operating within. All CRUD operations, searches, dashboards, and reports are scoped to this context. Users switch shelters via a selector.                                                                                |
| **Hard-Archive**             | A non-reversible archival action (e.g., shelter deletion) where all underlying data remains in the database for legal/audit purposes but is completely hidden from all user-facing views.                                                              |
