## Project Overview

Luna's Pet Central is a centralized, multi-shelter operations management platform for animal shelters. It replaces fragmented, paper-based processes with a unified digital solution covering the full operational lifecycle: pet registration and health tracking, pet lifecycle management, veterinary appointment management with a reusable directory of clinics and professionals, pet care scheduling with proactive reminders, categorized inventory control, maintenance scheduling, and public profile sharing for veterinarians and potential adopters.

**Primary Goals**:
1. Provide a single authoritative source of truth for all pet and shelter data.
2. Eliminate the risks associated with paper-based record management.
3. Enable controlled, role-governed access to sensitive data.
4. Support multi-shelter operations with a flexible shelter creation and administration model.
5. Enable transparent data sharing with veterinary partners and adoption candidates via configurable, revocable shareable links.
6. Track the complete lifecycle of each pet from intake through adoption, transfer, foster, or death.

**Business Reasoning**: The organization currently operates without any digital management system. The inability to efficiently track and retrieve pet medical histories, manage supplies, and coordinate maintenance represents a significant operational risk and limits the shelter capacity to scale.

### Shelter Context

A user operates within one active shelter context at a time. All CRUD operations, searches, dashboards, and reports are scoped to that active shelter. Users can switch shelters through a selector.

#### Authentication & User Management

| ID | Description | Acceptance Criteria | Remarks |
| :--- | :--- | :--- | :--- |
| FR01 | **User registration and authentication via Google SSO** — Users sign in through Google SSO to create an account. First-time sign-in creates a platform account. Subsequent sign-ins authenticate the existing account. | Given a user navigating to the sign-in page, When they complete Google SSO authentication for the first time, Then the system creates a new platform account linked to their Google identity and redirects them to the home screen. Given a returning user, When they complete Google SSO authentication, Then the system authenticates their existing account and redirects them to the home screen. | Google SSO is the sole authentication method. No local username/password. |
| FR02 | **Shelter creation** — Any authenticated user can create a new shelter. The creator automatically becomes the shelter's Admin. | Given an authenticated user with no existing shelters, When they submit a valid shelter creation form (shelter name, details), Then the system creates the shelter and assigns the user the Admin role for that shelter. Given an authenticated user who already administers other shelters, When they create a new shelter, Then they become Admin of the new shelter independently of their roles elsewhere. | There is no global Super Admin role. Admin authority is always scoped to a single shelter. |
| FR03 | **Staff invite link generation and redemption** — Admins can generate Identity-Bound invite links for staff not yet registered by inputting the invitee's email. Invited staff click the link and sign in via Google (email must match) to join the shelter with a designated role. Admins can use a "Resend Invite" function. Resending an invite immediately invalidates the previous pending invite link for that email address within that specific shelter. | Given an Admin of a shelter, When they generate an invite link with a target email and role, Then the system produces a unique, single-use URL that encodes the shelter ID and target role. Given a person who clicks an invite link, When they complete Google SSO and their email matches the invite, Then the system assigns them to the shelter with the specified role. Given an Admin viewing pending invites, When they click "Resend Invite", Then a new notification/email is dispatched and the previous pending invite link is invalidated. | Invite links are single-use and expire after 30 days if unused. |
| FR04 | **Role-based access control (Admin, Staff, Read-only) per shelter** — The system enforces three roles per shelter: Admin (full access including shelter settings and user management), Staff (full record read/write), and Read-only (read access only). | Given an Admin of a shelter, When they change a user's role from Staff to Read-only, Then the user immediately loses write access and can only view records. Given a Read-only user, When they attempt to create, edit, or delete any record, Then the system denies the action and displays an authorization error. Given a Staff user, When they attempt to access shelter settings or user management, Then the system denies the action. | Role changes take effect immediately. Users can hold different roles in different shelters. |

#### Pet Management

| FR06 | **Adoption availability flag toggle** — Staff can toggle an 'Available for Adoption' boolean flag on a pet profile. | Given a Staff user viewing a pet profile with 'Available for Adoption' set to false, When they toggle it to true, Then the system updates the flag and the pet appears in adoption-eligible views. Given a pet whose outcome is set to any archived status (Adopted, Deceased, Transferred), When a user views the profile, Then the 'Available for Adoption' toggle is disabled and set to false. | Archiving a pet automatically clears this flag. |
| FR07 | **Pet media upload (photos/videos)** — Staff can upload one or more photos and videos to a pet's profile. | Given a Staff user on a pet's profile, When they upload a valid image or video file, Then the file is stored, associated with the pet, and immediately visible on the profile. Given a Staff user uploading a file exceeding the maximum allowed size, When submission occurs, Then the system rejects the upload and displays an error with the size limit. | Media is included in both Adoption and Veterinary shareable link views. |
| FR08 | **Pet lifecycle outcomes (Adopted, Deceased, Transferred, In Foster)** — Staff set a pet's outcome to one of: Adopted, Deceased, Transferred (Internal), Transferred (External), or In Foster. Setting Adopted, Deceased, or Transferred archives the pet. In Foster is a reversible non-archived status. | Given a Staff user setting a pet's outcome to 'Deceased', When they confirm, Then the system archives the pet: full history is preserved, the pet is removed from active operational views and dashboard counts, and the 'Available for Adoption' flag is cleared. Given a Staff user setting a pet's outcome to 'In Foster', When they confirm, Then the pet remains in the active list but is tagged as 'In Foster' in all views. Given a Staff user returning a fostered pet, When they clear the 'In Foster' status, Then the pet returns to normal 'Active' status. | 'In Foster' does not archive the pet. All other outcomes archive. See FR09 for Adopted specifics and FR10 for Internal Transfer specifics. |
| FR09 | **Adopter details capture on adoption** — When a pet's outcome is set to 'Adopted', the system requires Adopter Details (Name, Phone, Address) before completing the archival. | Given a Staff user setting a pet's outcome to 'Adopted', When the adoption form is presented, Then the system requires Name, Phone, and Address fields to be filled. Given the staff submits the adoption form with all adopter details completed, When confirmed, Then the system archives the pet, stores the adopter details linked to the pet record, and clears the 'Available for Adoption' flag. Given the staff attempts to submit without completing all adopter detail fields, When they click confirm, Then the system prevents submission and highlights the missing fields. | Adopter details are stored as part of the archived pet record and are visible only to authenticated shelter staff. |
| FR10 | **Shadow record creation for internal transfers** — When a pet is transferred internally (to another Luna's Pet Central shelter), the system creates a 'Shadow Record': the original shelter retains a read-only copy of the pet's full history, and the receiving shelter gets a new active profile that references the original. Active temporary treatments and pending recurring care events are migrated to the receiving shelter's new active profile to preserve care continuity. External transfers simply archive the pet at the originating shelter. | Given a Staff user at Shelter A setting a pet's outcome to 'Transferred (Internal)' and selecting Shelter B as the destination, When they confirm, Then the system: (a) archives the pet at Shelter A with full history preserved as read-only, (b) creates a new active pet profile at Shelter B pre-populated with data from the original, migrating active treatments and pending care events, and a reference link to the original record. Given a Staff user setting a pet's outcome to 'Transferred (External)', When they confirm, Then the system archives the pet at the originating shelter with no shadow record created. | The shadow record at the original shelter is immutable. The new profile at the receiving shelter is independently editable. |

#### Notifications

| ID | Description | Acceptance Criteria | Remarks |
| :--- | :--- | :--- | :--- |
| FR24 | **Two-tier notification delivery (Standard in-app + Custom email/push)** — All notifiable events support two delivery modes: Standard (in-app only) and Custom (staff configure per event whether email and/or push notification is also sent in addition to in-app). | Given a Staff user configuring an inventory alert with Custom mode (email + push), When the alert triggers, Then the system delivers an in-app notification and also sends an email and a push notification. Given a Staff user leaving the notification mode as Standard, When the event triggers, Then only an in-app notification is delivered. | In-app notifications are always delivered regardless of the configured mode. |
| FR25 | **Notification delivery status tracking and failure escalation** — The system tracks the delivery status of every notification. If email or push delivery fails after 3 retry attempts, the notification is flagged as 'FAILED'. To prevent endless retry loops, the system temporarily auto-suppresses delivery for a specific user's channel after repeated consecutive failures, and displays an in-app banner to the recipient that must be acknowledged. Auto-suppression is triggered after 3 consecutive delivery failures on the same channel for the same user. The suppressed channel is automatically re-enabled when the user acknowledges the failure banner. Admins can also manually re-enable a suppressed channel from the user management screen. | Given an email notification that fails on the first attempt, When the system retries and succeeds on the second attempt, Then the notification is marked as 'Delivered' and no banner is shown. Given a push notification that fails all 3 retry attempts, When the final retry fails, Then the notification is flagged as 'FAILED', delivery to that channel is temporarily auto-suppressed, and an in-app banner is displayed with failure details. Given a user viewing a failure banner, When they click 'Acknowledge', Then the banner is dismissed and the acknowledgment is logged. | The retry interval and backoff strategy are implementation details. The 3-retry limit and auto-suppression are firm requirements. Auto-suppression triggers after 3 consecutive failures per user per channel. Re-enabled on banner acknowledgment or by Admin action. |

### Non-Functional Requirements

*(Note: Security, reliability, and quality attributes are captured as regular NFRs. All requirements are quantified and measurable.)*

| ID | Description | Remarks |
| :--- | :--- | :--- |
| NFR01 | **Usability** — The system shall provide an interface that is intuitive and usable by shelter staff with varied levels of technical proficiency, requiring minimal onboarding. Common tasks (e.g., registering a pet, logging a care event, creating a maintenance task) must be completable in fewer than 5 clicks from the dashboard. | Onboarding should not require formal training sessions; contextual help and clear labels suffice. |
| NFR02 | **Performance** — 95% of all page loads shall complete in under 2 seconds. Search queries shall return results in under 300 milliseconds. Dashboard rendering shall complete in under 1 second. | Measured under normal operating conditions (up to 50 concurrent users). |
| NFR03 | **Availability** — The system shall maintain 99.5% uptime measured monthly, excluding scheduled maintenance windows communicated at least 24 hours in advance. | — |
| NFR04 | **Scalability** — The system shall support at least 50 concurrent users across 10 shelters without performance degradation below the thresholds defined in NFR02. | Architecture must accommodate horizontal scaling for future growth. |
| NFR05 | **In-app notification reliability** — In-app notifications shall be delivered to all targeted recipients within 5 seconds of the triggering event. | Covers all notification types: care events, inventory alerts, maintenance tasks, reminders. |
| NFR06 | **Email/push notification reliability** — Email and push notifications shall be delivered within 60 seconds of the triggering event under normal conditions. A 3-retry policy with backoff shall be applied on delivery failure before escalation (see FR25). | — |
| NFR07 | **Access control enforcement** — All system features shall be gated by the user's assigned role within a shelter. Read-only users cannot create, edit, or delete records. Write access is restricted to Staff-level and above. Shelter settings and user management are restricted to Admins. | Role enforcement is validated server-side on every request. |
| NFR08 | **Data isolation** — Users can only access data within shelters they have been assigned to. Data-layer enforcement prevents cross-shelter data leakage regardless of client-side state. | No global platform administrator role exists; access is always scoped to specific shelters. |
| NFR09 | **Medical data privacy** — A pet's full medical history, veterinary documents, treatment records, and media are accessible only to authenticated, authorized shelter staff — or via an explicitly generated Veterinary Profile link. | Adoption Profile links must never expose medical data. |
| NFR10 | **Link anonymity** — Shareable profile links shall not expose any internal system identifiers, user account information, or metadata beyond the explicitly defined data subset for that link type. | Link URLs must use opaque, non-sequential tokens. |
| NFR11 | **Asset protection** — Uploaded veterinary documents and pet media (photos/videos) must not be accessible via guessable or enumerable public URLs. Access requires authentication or a valid active shareable link. | Implementation must ensure secure, expiring access tokens for media assets. |
| NFR12 | **Link integrity** — Revoked and expired shareable links must be immediately and permanently invalidated. Accessing a revoked or expired link must return a clear, non-revealing denial response with no cached or stale data. | — |
| NFR13 | **Audit logging** — The system must log all significant actions: user account creation and role changes, record creation and modification, document and media uploads, shareable link generation/renewal/revocation, pet outcome status changes, notification delivery failures, and inventory adjustments. Logs must be accessible to Admins of the relevant shelter. | Audit logs are append-only and not editable by any user. |
| NFR14 | **Notification privacy** — Email and push notification bodies must not contain sensitive pet medical data. Notifications shall include a summary and a prompt directing the user to log in for details. | Applies to all Custom-mode (email/push) notifications. |
| NFR15 | **Backup & disaster recovery** — The system shall perform daily automated backups. Recovery Point Objective (RPO) shall be less than 24 hours. Recovery Time Objective (RTO) shall be less than 4 hours. | Backup integrity should be validated periodically via restore tests. |
| NFR16 | **Data retention & GDPR Deletion** — All records are kept indefinitely. The system must support a "Data Deletion Request" workflow where an Admin requests deletion, followed by a 7-day cooling-off period before hard-deletion. During the 7-day cooling-off period, the requesting Admin may cancel the deletion request with a single click, restoring the data to its previous state. After the 7 days, the request is irrevocable. The system explicitly mandates "Tombstoning" (replacing PII with `[GDPR ERASURE VERIFIED]`) in the immutable audit logs instead of dropping rows. | Hard-delete is an administrative action following a 7-day cooling-off period. |
| NFR17 | **Global Search** — The system shall provide a persistent global search bar accessible from any view, supporting fuzzy matching and autocomplete for pets, inventory, and maintenance tasks. | Global Search is scoped to the active shelter context. |

## Technical Process Flow

The following describes the logical workflow of the primary operational processes within Luna's Pet Central.

### 1. User Registration and Shelter Setup Flow
1. A new user navigates to the sign-in page and authenticates via Google SSO.
2. On first authentication, the system creates a platform account linked to their Google identity.
3. The user creates a new shelter by providing a shelter name and details.
4. The system assigns the user as Admin of the new shelter.
5. The Admin generates Identity-Bound invite links by entering invitees' emails and assigning designated roles (Staff or Read-only).
6. Team members click their invite link and authenticate via Google SSO (email must match the invite).
7. On successful authentication, the system assigns the invited user to the shelter with the specified role.
8. Admins can use the "Resend Invite" function for pending invitations.

### 2. Pet Registration Flow
1. Authenticated Staff or Admin member initiates a new pet registration.
2. Staff completes the registration form including intake origin selection (if 'Other' is selected, a secondary free-text field appears), health details, and optionally checks the 'DOB Estimated' flag.
3. Staff optionally toggles the 'Available for Adoption' flag.
4. System validates required fields and creates the pet profile record.
5. The pet profile is immediately available to all authorized staff at the shelter.

### 3. Veterinary Appointment Flow
1. Staff creates a new appointment record linked to a specific pet.
2. Staff selects the clinic and veterinarian from the directory (or adds a new entry).
3. Staff enters appointment date and notes.
4. Staff optionally creates care events directly within the appointment, which are auto-linked.
5. Staff uploads any received documents (PDFs or images) as attachments.
6. Appointment record, care events, and attachments are stored on the pet's profile.

### 4. Pet Care Event Flow
1. Staff creates a care event record for a pet, selecting the modality.
2. If applicable, staff enters the substance/product name (optional).
3. Staff configures the recurrence interval and end date (if temporary).
4. Staff optionally links the event to an existing vet appointment.
5. Staff optionally selects an inventory item and decrement quantity (inventory usage template, FR21). If stock is insufficient, the system warns and saves the care event without the inventory decrement.
6. System schedules future occurrences and triggers proactive reminders at 7 days, 3 days, and 1 day before each occurrence is due (FR18), plus an on-due-date notification (FR17).
7. Staff log completion of each event instance as it occurs.

### 5. Inventory Management and Alert Flow
1. Staff logs a new inventory item, selecting a category and entering all required fields.
2. Staff configures alert rules for the item (quantity threshold or expiry window).
3. Staff configures notification mode: Standard (in-app) or Custom (+ email and/or push).
4. System evaluates inventory levels against configured rules continuously.
5. When a rule triggers, the system delivers notifications in the configured mode.
6. If email/push delivery fails after 3 retries, the system flags the notification as 'FAILED' and displays a non-dismissible in-app banner to the intended recipient until acknowledged (FR25).
7. Staff manually update quantity when items are consumed or restocked (or use inventory usage templates from care events, FR21).

### 6. Maintenance Task Flow
1. An authorized Staff or Admin member creates a maintenance task with type, description, and scheduled date.
2. Staff optionally assigns the task to a specific staff member.
3. All shelter staff receive a notification (Standard or Custom). If assigned, the assignee receives an additional individual notification.
4. Staff mark the task as completed when finished; the system logs the completion event.
5. Overdue tasks remain visible and trigger reminders.

### 7. Profile Sharing Flow
1. Staff navigates to a pet's profile.
2. For Adoption Profile links: the pet must have the 'Available for Adoption' flag active.
3. Staff selects link type (Adoption or Veterinary) and configures TTL (maximum 90 days).
4. System generates an anonymous URL with the appropriate visibility scope.
5. Staff shares the URL with the intended recipient.
6. Recipient accesses the link without a system account.
7. Before a link expires, Staff can renew it to reset the TTL (maximum 90 days from renewal).
8. Staff can navigate to the link management view and manually revoke any active link at any time.

### 8. Pet Archiving and Transfer Flow
1. Staff navigates to a pet's profile and sets the outcome status (Adopted, Deceased, Transferred Internal, Transferred External, or In Foster).
2. **If 'Adopted'**: System presents the Adopter Details form (Name, Phone, Address). Staff must complete all fields before the adoption is finalized. On confirmation, the pet is archived with adopter details stored.
3. **If 'Deceased'**: System archives the pet immediately. Full history is preserved.
4. **If 'Transferred (Internal)'**: Staff selects the destination shelter (must be another Luna's Pet Central shelter). System creates a shadow record — original shelter keeps a read-only copy of the full history, destination shelter receives a new active profile referencing the original.
5. **If 'Transferred (External)'**: System archives the pet at the originating shelter with no shadow record.
6. **If 'In Foster'**: Pet status is updated to 'In Foster' without archiving. Pet remains in active views. When the pet returns, staff clear the 'In Foster' status.
7. For all archiving outcomes: the 'Available for Adoption' flag is automatically cleared, pending care events are cancelled (see Edge Cases), and the pet is removed from active operational views and dashboard counts.
8. All active shareable links are automatically revoked. The system strictly forbids creating new shareable links for the archived pet.

### 9. Notification Failure Escalation Flow
1. A notifiable event triggers (care event reminder, inventory alert, maintenance task).
2. System delivers the in-app notification immediately (always delivered).
3. If the user has configured Custom mode, the system attempts email and/or push delivery.
4. On delivery failure, the system retries up to 3 times with backoff.
5. If all retries fail, the notification is flagged as 'FAILED'.
6. System displays a non-dismissible in-app banner to the intended recipient containing the failure details and the original notification content summary.
7. The banner persists until the recipient clicks 'Acknowledge'.
8. Acknowledgment is logged in the audit trail.

---


### 10. Report Generation and Consumption

1. **Initiate**: Admin or Staff selects a report type (e.g., Pet Census, Inventory Status) and configures filters.
2. **Query**: The system queries the database, strictly scoped to the active shelter context.
3. **Render**: The system renders the results on-screen with pagination for large datasets.
4. **Export**: The user optionally exports the full dataset (e.g., CSV/PDF format).

### 11. Dashboard and Search Usage

1. **Dashboard Load**: User navigates to the Dashboard view.
2. **Aggregation**: The system calculates and displays key KPIs (active pets, pets in treatment, inventory alerts) for the active shelter.
3. **Search Initiation**: User inputs a query into the Global Search bar.
4. **Result Rendering**: The system returns matched results across pets, inventory, and maintenance tasks within the shelter context.
5. **Navigation**: User selects a result to navigate directly to its detail view.

## Edge Cases

The following documents expected system behavior during edge-case scenarios:

| Scenario | Expected Behavior |
| :--- | :--- |
| **Deleted appointment linked to care events** | Soft delete is performed. The appointment is removed from active views. Each linked care event displays the placeholder text: 'Originally linked to appointment [DELETED: YYYY-MM-DD]'. The care event remains fully operational. |
| **Last Admin leaves a shelter** | The system prevents the last Admin from removing themselves or being removed. If they wish to leave, they must first promote another user to Admin. If no other users exist in the shelter, the Admin may delete the shelter entirely (which archives all data). Shelter deletion requires a confirmation workflow (e.g., typing 'DELETE CONFIRM' + re-authentication). It is a hard-archive action. All underlying data remains in the database for legal/audit purposes but is completely hidden from all non-administrative views. |
| **Duplicate pet profiles** | The system does not enforce uniqueness on pet profiles (animals may share names, breeds, etc.). Staff should use manual review to identify duplicates. A future enhancement may add a duplicate-detection warning based on name + species + DOB, but this is out of MVP scope. |
| **Upload failure mid-transfer** | If a file upload fails mid-transfer (network interruption, timeout), the system discards the partial upload and displays an error prompting the user to retry. No partial files are persisted. |
| **Notification delivery failure after retries** | After 3 failed email/push retries, the notification is flagged as 'FAILED'. A non-dismissible in-app banner is shown to the intended recipient until they acknowledge it. The original triggering event is not affected. |
| **Expired/revoked link accessed** | The system returns a clear, non-revealing denial page (e.g., 'This link is no longer available'). No pet data, error details, or internal identifiers are exposed. The response indicates the resource is permanently unavailable. |
| **Archived pet with active care events** | When a pet is archived (Adopted, Deceased, Transferred), all pending/future care event occurrences for that pet are automatically cancelled. Completed past occurrences are preserved in the archive. Proactive reminders for cancelled events are suppressed. All active shareable links are automatically revoked, and new links cannot be created. |
| **Shelter merged/closed** | Shelter closure is an Admin action. All pets must be individually resolved (transferred or archived) before the shelter can be marked as closed. A shelter with active pets cannot be closed. Closed shelters retain all historical data in read-only mode. |
| **Concurrent inventory edits by multiple staff** | The system must ensure that concurrent edits must not silently overwrite data. If two staff members edit the same item simultaneously, the second save is rejected with a conflict error and a prompt to refresh and retry. The conflict resolution prompt must include a data comparison view that displays: "Another staff member updated this item. The current value is [X]. Your value is [Y]. Please reconcile and re-enter." |
| **Pet transferred internally then externally from new shelter** | The new shelter treats the pet as its own active profile. When the new shelter transfers the pet externally, it archives the pet at the new shelter. The original shelter's shadow record remains unchanged and read-only. |
| **Adopter details missing when setting Adopted status** | The system requires all Adopter Detail fields (Name, Phone, Address) before completing the adoption archival. If any field is missing, submission is blocked with validation errors. The pet remains in its current status until adoption is finalized. |
| **DOB is approximate (estimated flag)** | When 'DOB Estimated' is checked, the date is stored normally but displayed with an '(Estimated)' label in all views, reports, shareable links, and exports. No age-based calculations change — the estimated date is treated as the canonical DOB. |
| **Intake origin 'Other' handling** | When 'Other' is selected from the intake origin dropdown, a secondary free-text field appears and is required. The system stores the value as enum 'OTHER' with the free-text description. Reports group 'OTHER' entries together; the free-text is available on drill-down. |
| **Google SSO provider temporarily unavailable** | The system displays a clear, branded error page informing the user that authentication is temporarily unavailable and advising them to retry shortly. No fallback authentication method is provided. All authenticated sessions already in progress remain valid until their natural expiry. No data is lost. |
| **Staff attempts to transfer a pet to a closed/deleted shelter** | The system prevents the transfer. The closed/deleted shelter does not appear in the destination shelter selector. If the shelter was closed after the transfer was initiated but before confirmation, the system rejects the transfer with a clear error message and the pet remains at the originating shelter in its current status. |
| **Pet with active shareable links is transferred internally** | All active shareable links for the pet at the originating shelter are automatically revoked upon transfer (consistent with archival behavior). The new active profile at the receiving shelter starts with zero shareable links. Staff at the receiving shelter may generate new links as needed. |
| **Email mismatch on invite redemption** | The system rejects the redemption attempt with a clear error indicating the invite is bound to a different email address. The user is prompted to sign in with the correct account or request a new invite. |
| **Expired invite link access** | The system returns a clear error indicating the invite has expired. The user is prompted to request a new invite from the shelter admin. |
| **Duplicate shelter names** | The system does not enforce global uniqueness for shelter names (since they are isolated tenants). Two users can create shelters with the same name. Uniqueness is enforced via internal shelter IDs. |
| **Duplicate vet directory entries** | The system does not enforce strict uniqueness for vet directory entries, but warns the user if an entry with a similar name or email already exists. |
| **Deleting a vet entry referenced by existing appointments** | The system prevents hard-deletion of the entry. Instead, it offers to soft-delete the entry (hiding it from new searches but preserving it for existing appointments). |
| **Retroactive appointment validation** | Appointments can be logged with dates in the past, but the system displays a warning to confirm the retroactive entry is intentional. |
| **Care event created with < 7 days until due** | The system schedules the event and only sends the applicable reminders (e.g., if created 2 days before, it only sends the 1-day reminder and on-due-date notification). Past reminders are skipped. |
| **Search yields empty results** | The system displays a clear "No results found" state, avoiding raw database errors. |
| **Large datasets in reports** | The system paginates large reports on-screen and provides an asynchronous export option for datasets exceeding 1000 rows. |
| **Stale dashboard data** | The dashboard caches data for performance, but automatically refreshes when the user navigates back to it or after 5 minutes of inactivity. A manual refresh button is also provided. |

**Transitions:**

- `Retrying (2) → Retrying (3)`: Third attempt fails.

- `Retrying (3) → Failed`: All 3 retry attempts exhausted. In-app banner displayed.
- `Failed → Acknowledged`: User acknowledges the failure banner. Acknowledgment logged.

## Domain Model

Conceptual model of the core domain entities and their relationships:

```
Shelter
 ├── Users (Admin, Staff, Read-only)
 ├── Invite Links
 ├── Pets
 │     ├── Care Events
 │     │     └── Inventory Usage (optional link)
 │     ├── Vet Appointments
 │     │     └── Documents (PDF, Images)
 │     ├── Photos / Videos
 │     ├── Shareable Links
 │     └── Adopter Details (on adoption)
 │
 ├── Inventory Items
 │     └── Alert Rules
 │
 ├── Maintenance Tasks
 │
 └── Notifications
       └── Delivery Status
```

**Key Relationships:**
- A **Shelter** contains all other entities. Data isolation is enforced at this boundary.
- A **User** can belong to multiple Shelters with different roles in each.
- A **Pet** belongs to exactly one Shelter (active profile). A shadow record may exist at a previous shelter for internally transferred pets.
- A **Care Event** belongs to a Pet and may optionally link to one Vet Appointment and one Inventory Item (usage template).
- A **Vet Appointment** belongs to a Pet and references entries in the Veterinary Directory. It may have multiple Documents attached.
- A **Shareable Link** belongs to a Pet and has a type (Adoption/Veterinary), TTL, and lifecycle status.
- An **Inventory Item** belongs to a Shelter and may have multiple Alert Rules.
- A **Maintenance Task** belongs to a Shelter and may be assigned to a User.
- A **Notification** is generated by the system for a triggering event and targets one or more Users. It tracks Delivery Status per channel (in-app, email, push).
- **Adopter Details** are a one-to-one association with a Pet, populated only when the pet's outcome is set to 'Adopted'.
- **Invite Links** are generated by Admins, scoped to a Shelter, single-use, Identity-Bound to a specific email, and expire after 30 days. Resending an invite invalidates the previous pending link.

## Considerations

### Risks

| Risk | Description | Mitigation |
| :--- | :--- | :--- |
| Data Migration | No existing digital records to migrate, but paper records may need manual entry at go-live. | Plan for a structured data entry period at launch with clear staff guidelines. |
| User Adoption | Staff with limited technology experience may resist the new system. | Prioritize simple, intuitive interface design (NFR01) and provide staff orientation. |
| Media and Document Storage Volume | Pet photos, videos, and veterinary documents may grow to significant storage volumes over time. | Design storage capacity with scalability and file size limits from the outset. |
| Notification Reliability | Staff must trust that in-app, email, and push alerts will arrive consistently and correctly. | Implement reliable notification delivery with a 3-retry policy and failure escalation (FR25). |
| Shareable Link Misuse | Veterinary Profile links contain sensitive medical data; if shared with the wrong recipient, this is a data exposure risk. | Require explicit confirmation step when generating a Veterinary link; support instant revocation (NFR12); enforce maximum 90-day TTL (FR27). |
| Google SSO Dependency | Platform authentication is fully dependent on Google SSO availability. | Monitor Google SSO service status; display a clear error page if SSO is temporarily unavailable. No fallback authentication method is in scope for MVP. |
| Shadow Record Data Integrity | Internal transfers create linked records across shelters; data inconsistency or orphaned records are a risk. | Shadow records are immutable at the originating shelter. The new active profile at the destination is independent. Referential link is maintained but does not create a data dependency. |
| Concurrent Access Conflicts | Multiple staff editing the same inventory item or pet record simultaneously could cause data loss. | Implement conflict detection with data comparison prompts (see Edge Cases). |

### Assumptions

- The initial deployment covers a single shelter location; multi-shelter support is required in the MVP and will be exercised as the organization grows.
- All shelter staff will have access to a device capable of accessing the platform and have a Google account for authentication.
- Shelter Admins are responsible for inviting and managing staff within their shelter via invite links.
- Veterinary documents are assumed to be received digitally (scanned or photographed) before upload.
- Records are kept indefinitely; hard-delete is supported only for verified GDPR compliance requests (NFR16).
- Each shelter operates independently — there is no cross-shelter data sharing beyond internal pet transfers (shadow records).

### Dependencies

- **Google SSO**: Platform authentication depends on Google's OAuth/SSO service availability.
- Consistent internet connectivity is required for all platform features.
- Staff must be able to digitize (scan/photograph) paper veterinary documents before upload.
- Email delivery (for Custom notifications) depends on a functioning email delivery integration.
- Push notification delivery depends on device registration and notification permission grants from staff.

### Constraints

- MVP scope excludes: adoption payment processing, public donation management, volunteer shift scheduling, and automated duplicate pet detection.
- Inventory stock levels are adjusted manually by staff — except when using the optional 1-click inventory usage template during care event recording (FR21), which decrements the specified quantity.
- Access is always scoped to specific shelters; there is no global platform administrator role (NFR08).
- Shareable links have a maximum TTL of 90 days and cannot be made permanent (FR27).

| **In Foster** | A pet lifecycle outcome status indicating the animal has been placed in a temporary foster home but remains under the shelter's responsibility. |
| **Adopter Details** | Contact information (Name, Phone, Address) captured for the person adopting a pet, stored securely and accessible only to authorized shelter personnel. |
| **DOB Estimated Flag** | A boolean flag on a pet profile indicating that the recorded date of birth is an estimate rather than a known date. |
| **Shareable Profile Link** | A URL generated by the system granting anonymous, read-only access to a defined subset of a pet's profile data. |
| **TTL** | Time-to-Live — a configurable duration (maximum 90 days, renewable) after which a shareable link automatically expires. |
| **Intake Origin** | The source from which a pet arrived at the shelter (e.g., street rescue, owner surrender). |
| **Archived Pet** | A pet whose outcome status has been set (Adopted, Deceased, Transferred). Its full history is preserved but it no longer appears in active operational views. |
| **Inventory Alert** | A system notification triggered when an inventory item reaches a configured quantity threshold or approaches its expiration date. |
| **Care Event** | A recorded instance of a treatment, vaccine, vermifuge, or other care activity administered to a pet. |
| **Vet Directory** | A shared, searchable registry of veterinary clinics and professionals maintained within the platform. |
| **Tombstoning** | A data deletion technique where the record is not physically removed from the database, but its sensitive PII fields are replaced with a predefined placeholder (e.g., `[GDPR ERASURE VERIFIED]`) to maintain referential integrity in immutable logs. |
| **Shelter Context** | The active shelter a user is operating within. All CRUD operations, searches, dashboards, and reports are scoped to this context. Users switch shelters via a selector. |
| **Hard-Archive** | A non-reversible archival action (e.g., shelter deletion) where all underlying data remains in the database for legal/audit purposes but is completely hidden from all user-facing views. |
